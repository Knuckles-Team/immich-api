## What the checks establish

The generated inventory records every source operation, its effective security
declaration and vendor extensions. The packaged canonical compiler checks that
the contract retains every operation and its exact method, route, parameter and
response schemas. Native discovery initially lists only `search_tools` and
`call_tool`. Exact searches retrieve each complete domain schema and compare it
with the contract, including FastMCP's actual reference expansion. The additional
album metadata tool is also measured against the same disclosure budget.

`tests/test_operation_parity.py` then calls each operation through the real API
client and an actual native MCP client through FastMCP's `call_tool` proxy.
HTTPX's mock transport is the only
provider boundary replacement. The mock checks request method, path, query,
headers and JSON, form or multipart body; the test checks the complete typed
response. Successful operation IDs must cover the source exactly, with no
missing, extra or duplicate entries.

MCP writes must complete the SDK confirmation flow under protocol `2026-07-28`.
The tests do not replace the confirmation helper or select a legacy protocol.
Every write is also checked with operator write mode disabled. Explicit denial
must produce no HTTP request, and 403, 429 and 503 errors must produce only one
HTTP attempt for each declared method. These requests use synthetic fixtures
and an `.invalid` origin. They do not mutate or certify the live provider.

Run the tests in the approved environment containing the repository's declared
dependencies:

```bash
python -m pytest tests/test_operation_parity.py -q
python scripts/generate_tool_schemas.py --check
python scripts/generate_immich_content.py --check
```

The normal pre-push hook runs the complete test suite. Source dependencies and
scanner revisions must accompany any reported validation result; a collection
count or successful tool listing is not dispatch evidence.

```bash
  --provider-overlay api-spec/immich.provider-evidence.json \
  --expected-overlay-sha256 43f936578e5361b4400750ccb9e04747948eabe19baad0e78d90774c9c79c432 \

```

Provider source at commit `60b51cb3bc909e72fe963f4dfb1947515cb9ab3b` explicitly
marks the 17 routes public at the normal account authentication guard. This does
not mean each operation is unrestricted. Password login still checks a password;
admin signup and restore initialization require setup to be available; OAuth
callback and logout require their respective proofs; maintenance login requires
a valid maintenance token while maintenance mode is active. Public maintenance
status reveals additional detail only for a valid token. The guard checks setup
before admitting a public route. The source review retains these preconditions
and does not change runtime authorization or enable writes.

## Provider export differences

The served schema and Immich's checked-in SDK schema are not byte-identical.
Replaying the provider's `patchOpenAPI` export transforms produces exact object
equality with its checked-in 3.2.2 schema. The transforms sort required fields and
parameters, remove three `propertyNames` entries and one binary `contentEncoding`
entry for OpenAPI 3.0 compatibility, and convert `x-immich-required` on
`AssetMediaCreateDto.assetData` into a standard required field.

The connector preserves the served source bytes and constraints. The reviewed
sidecar makes only the additive `assetData` required-field correction; it removes
no constraints and changes no operation or security objects. The effective source
SHA256 is `4733e4346a7c22cfdac9eb9cbb5298f42662c8b3f5b3cc450cfd2d4347e60e77`.
The equivalence
check is provenance evidence, not permission to discard validation constraints.
The upload fixture includes the required asset file. The no-file multipart
regression covers only the backup upload whose source schema permits that shape;
it establishes serialization, not successful live backup processing.

Unicode property patterns are translated into literal ranges from pinned Unicode
18 data matching the reviewed `regex` runtime. Positive and negative examples and
all code points in the supported letter, mark and number categories are checked.
Unsupported property syntax fails rather than losing its constraint. This records
the converter's Unicode semantics; it does not claim a deployed Node runtime's
Unicode version.

The earlier eager catalog measured about 4.6 MB. The current server supports
`IMMICH_API_MCP_CLIENT_BUDGET`, an operator-provided JSON file path specifying
a named client, discovery mode, and input/output/tool/listing/search byte limits.
With `regex-search`, the entire underlying catalog remains available while each
search returns at most one complete schema. Oversized schemas fail explicitly;
constraints are never truncated. No budget is inferred from the generated size.

`tests/fixtures/native-client-budget.json` defines a synthetic FastMCP 4.1.0 test
client with 1 MiB schema/tool/search limits and a 16 KiB initial listing limit.
The exhaustive suite configures this through the ordinary server setting and
checks initial disclosure, all 41 domain schemas, the album sample schema, and
every operation through the proxy. These limits are test inputs, not approval for
any production model. An operator must supply a supported production client
budget and run native admission with that same runtime configuration before
operational readiness can be assessed.

Live endpoint checks, credential scope, source-built images, fleet composition and
graph receipt/readback remain separate acceptance work.
